Exception handling

Opening a file that is not there stops the program. A try and an except let the program print a message and carry on instead. It is a mark point in nineteen of the last twenty-nine mark schemes.

1

What an exception is

An exception is an error that happens while a program is running, rather than one the editor can see beforehand. The program stops at the line that caused it, and nothing after that line runs.

File = open("Missing.txt", "r")
for Line in File:
    print(Line)
File.close()
Traceback (most recent call last):
  File "crash.py", line 1, in <module>
    File = open("Missing.txt", "r")
FileNotFoundError: [Errno 2] No such file or directory: 'Missing.txt'

The code is correct. The file is the problem, and the file is outside the program's control: it can be missing, renamed, moved or locked by something else. Code that reaches outside itself has to allow for that, and the syllabus calls knowing when that applies part of understanding why exception handling matters.

Handling the exception means the program decides what happens next instead of stopping.

try:
    File = open("Missing.txt", "r")
    for Line in File:
        print(Line.strip())
    File.close()
except:
    print("Cannot open file")
Cannot open file

Key words

exception
An error raised while the program is running.
raise
What the program does when it meets an error it cannot continue past.
catch
To deal with an exception instead of letting it stop the program.
try block
The code that is being watched for an exception.
except block
The code that runs if one happens.
traceback
The report Python prints when an exception is not caught.
2

The shape in Python

The shape is two keywords, each with an indented block under it. Python runs the try block. If anything in it raises an exception, the rest of that block is abandoned and the except block runs instead.

try:
    Average = Total / Count
except:
    print("There were no values to average")
There were no values to average

The mark points are worded as exception handling with an appropriate output, so three things are needed and all three are checked:

  1. the try, with the risky code inside it
  2. the except
  3. an output that says what went wrong

An except block that does nothing, or that silently carries on, is not worth the mark. The message does not have to be long. print("Cannot open file") is enough, and it is what the published answers use.

There is no pseudocode for it

The Cambridge pseudocode guide has no exception handling commands, so a question describes it in words, usually as a line like include exception handling when writing to the file. The Python is the candidate's own.

Three languages, one idea

Python writes try and except. Java and Visual Basic write try and catch. The mark schemes list all three, which is why the mark point says try, catch, except.

3

What goes inside the try

Several mark schemes state it exactly: all file access within the try. Opening the file inside the try and then reading it outside loses the mark, and the program stops at the first line that uses the file.

✗ Only the open is guarded

try:
    File = open(Name, "r")
except:
    print("Cannot open file")

for Line in File:
    DataArray.append(Line.strip())
File.close()

✓ Everything is guarded

try:
    File = open(Name, "r")
    for Line in File:
        DataArray.append(Line.strip())
    File.close()
except:
    print("Cannot open file")

Run the first version against a filename that does not exist and both things happen:

Cannot open file
Traceback (most recent call last):
  File "part.py", line 6, in <module>
    for Line in File:
                ^^^^
NameError: name 'File' is not defined

The open() never finished, so the variable File was never created, and the loop that follows has nothing to work with. Putting the reading and the closing inside the try as well removes both problems at once: there is one path for the file working and one path for it failing.

The exact wording

Two mark schemes spell the requirement out rather than leaving it implied, awarding the mark for exception handling with all file access inside the try, an appropriate catch and an output.

4

When to use it

The syllabus asks candidates to know when exception handling is appropriate. The test is whether the thing that might fail is under the program's control.

SituationToolWhy
Opening, reading or writing a filetry and exceptThe file is outside the program. It can be missing, moved or unreadable.
Converting what a user typedtry and exceptThe user can type anything, and int() raises an exception rather than returning a value that can be tested.
Checking a number is in rangeIFThe value is already in the program and can simply be compared.
Checking an array is not fullIFThe program holds the pointer, so the condition can be tested directly.
Checking a stack is empty before poppingIFSame reason. A Paper 4 question asks for a returned value here, not a caught error.

Exception handling is not a replacement for validation. A question that says the function returns False when the queue is full wants an IF and a return, and wrapping the same code in a try answers a different question.

Converting what the user typed

Value = input("Enter a number ")
try:
    Number = int(Value)
    print(Number * 2)
except:
    print("That is not a number")
Enter a number forty
That is not a number

Test both paths

Run the program once with the file present and once with the filename spelled wrongly.

A try that has never been made to fail has not been tested, and a part asking for a screenshot is asking for proof that it was.

5

The errors it catches

A bare except catches everything, which is what the published answers use and what the marks accept. The name Python prints for an uncaught error says what went wrong.

ErrorCaused byWhat Python prints
FileNotFoundErroropen("Missing.txt")No such file or directory
ValueErrorint("forty")invalid literal for int() with base 10
IndexErrorReading past the end of an arraylist index out of range
TypeErrorFile.write(10)write() argument must be str, not int
ZeroDivisionErrorTotal / Count where the count is 0division by zero

Naming the error in the except line narrows what is caught, which is useful while a program is being written because a mistake in the code is then still reported rather than hidden behind the message.

except FileNotFoundError:
    print("Cannot open file")

Either form earns the mark. The bare except is shorter under exam conditions and cannot be caught out by an error arriving with a name that was not expected.

Why the message matters

A bare except hides every error in the block, including a typo in the code inside it.

A message that names the operation, rather than one that says Error, is what makes the difference visible while testing.

6

Common mistakes

✗ Only the open is inside the try

The message prints and the program then stops at the first line that uses the file.

✓ Put the open, the loop and the close inside the try.

Stated in the mark schemes as all file access within the try.

✗ The except block says nothing

A try with pass or an empty except hides the failure and earns nothing, because the mark point requires an output.

✓ print("Cannot open file")

Every mark point on this topic is worded with an appropriate output or message.

✗ Exception handling used instead of an IF

A question that asks for False to be returned when a structure is full is asking for a condition, not a caught error.

✓ Use try for what the program does not control, and IF for what it does.

The syllabus asks for knowing when exception handling is appropriate.

✗ No exception handling at all

The program runs perfectly in the exam room and still loses a mark, because the mark is for the handling rather than for the result.

✓ Wrap every file operation, whether the question mentions it or not.

June 2025 Paper 41 Question 2(a), where the question says nothing about it and the mark scheme lists it.

✗ The file is left open

Putting close() after the except block means it runs even when the file was never opened, which raises a second error.

✓ Close the file as the last line inside the try.

The mark schemes ask for the file closed in an appropriate place.

✗ The whole program is one try block

Wrapping everything means one message for every possible failure, and real mistakes in the code are swallowed along with the file ones.

✓ One try around the file work in the procedure that does it.

Each mark scheme attaches the handling to the procedure being written.

7

In the exam

Exception handling is never a question on its own. It is a mark point inside a question about a file, and in these papers it has never been asked about anything else.

How often

It is a mark point in nineteen of the twenty-nine mark schemes from June 2021 to November 2025. Thirteen of those question papers ask for it in the wording of the question, which means that in the other six the mark was there for candidates who added it without being told.

Where the mark sits

It is one of the points in a list that a part is marked against, so it is worth the same as opening the file or looping to the end of it. In June 2025 Paper 41 Question 2(c), five marks cover the header and the open, the loop, the write, the line break and the exception handling.

When the question asks in words

November 2025 Paper 42 Question 3(d) says to include exception handling when writing to the file. June 2025 Paper 41 Question 2(c) says the procedure uses exception handling when opening and writing data to the text file. Both describe it in English because there is no pseudocode form.

Evidence

The code copied into the evidence document is what is marked, so the try and the except have to be visible in the pasted code for the part they belong to.

Check your own handling

  • Is there a try in every procedure that touches a file?
  • Is the open, the loop and the close all inside it?
  • Does the except print something that names the problem?
  • Has it been run once with the file missing?
